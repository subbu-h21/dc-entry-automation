# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

The repo root only contains `dc-entry-automation/` — that's the whole project. Everything below is relative to that directory.

## Commands

### First-time setup
```
setup.bat
```
Creates `backend/venv`, installs `backend/requirements.txt`, installs `frontend/` npm deps, and copies `backend/.env.example` → `backend/.env`. After running it, fill in `backend/.env` (`OPENROUTER_API_KEY`, `ELEVENLABS_API_KEY`, `CRM_CLIENT_ID`, `CRM_CLIENT_SECRET`); `PRODUCT_LIST_PATH` already defaults to `../Product_List.xlsx` and only needs changing if that workbook lives somewhere else.

### Day-to-day development
Run backend and frontend separately so the frontend hot-reloads:
```
cd backend && venv\Scripts\activate && python main.py     # API on :3001 (PORT in .env)
cd frontend && npm run dev                                # Vite dev server on :5173, proxies /extract, /crm, /voice, /products, /suppliers, /staff, /inbox, /admin to :3001 (see vite.config.ts)
```
Use `http://localhost:5173` while developing — it has hot reload and the API proxy.

### Build / typecheck frontend
```
cd frontend && npm run build     # tsc (typecheck) && vite build → frontend/dist
cd frontend && npm run preview
```
There is no separate lint script and no ESLint/Prettier config — `npm run build`'s `tsc` step (strict mode, `noUnusedLocals`/`noUnusedParameters` on) is the only static check. There is no Python linter/formatter configured either.

### "Production" launch
```
start.bat
```
This is **not** the dev workflow above — it builds the frontend (`npm run build`), then starts only the backend (`python main.py`), which serves the API *and* the built SPA from `frontend/dist` via the catch-all route in `main.py`, on port 3001 (not 5173). It no longer launches a Cloudflare quick tunnel automatically — the phone-camera "inbox" flow now reaches the backend via a stable domain set up outside this repo, not a random `*.trycloudflare.com` URL. `tunnel.py` (a Cloudflare quick-tunnel + QR code script) still exists in the repo for ad-hoc use but isn't invoked by `start.bat` anymore.

### Tests
There is no test suite in this repo (no test files, no test runner configured) — verify changes by running the app end-to-end.

## Architecture

Two-part app under `dc-entry-automation/`: a FastAPI backend and a React/Vite/TS frontend, joined either by the Vite proxy (dev) or by FastAPI serving the built SPA directly (prod, see `main.py`'s catch-all `serve_spa` route).

### Request flow: image → filled DC form

1. **Extraction** (`routes/extract.py` → `services/openrouter.py`): 1–2 uploaded invoice page images (multi-page DCs — `images: list[UploadFile]`, capped at 2) plus an optional third "product packaging" photo for disambiguation are sent to a Gemini model via OpenRouter using forced tool-calling (`EXTRACTION_TOOL`) so the model returns structured JSON (`dc_number`, `dc_date`, `supplier_name`, `products[]`) instead of free text. When 2 invoice pages are sent, an extra prompt block tells Gemini they're consecutive pages of the same document and to combine every product row into one `products` array. The prompt encodes pharmacy-invoice-specific rules (e.g. the `"5+1"` free-qty notation, stripping MFR/HSN code columns from the product name) that later post-processing re-enforces as a fallback (`_fix_free_qty`, `_fix_expiry`, `_fix_batch` in `extract.py`).
2. **Product matching** (`services/product_matcher.py`, singleton in `services/matcher_instance.py`): a two-stage fuzzy match against the pharmacy's own catalog (`Product_List.xlsx`, sheet `data`, columns `PRODUCT`/`MANUFACTURER`/`PACK`, path from `PRODUCT_LIST_PATH`).
   - Stage 1 narrows ~2000 brand "heads" (first word of each product name) to ~20 via combined trigram + phonetic (pure-Python Double Metaphone) + `fuzz.ratio` signals, then asks Gemini to pick the right brand.
   - Stage 2 scores every SKU under that brand with `fuzz.WRatio` and asks Gemini to pick the exact SKU (dosage form / strength / combination-suffix rules are in the prompt).
   - Both stages return `top_candidates` so the frontend can offer a manual override if the AI pick is wrong.
3. **Supplier matching**: the extracted supplier string is fuzzy-matched (`rapidfuzz.WRatio`) against the CRM's supplier list (`services/crm_api.py`, cached for 5 minutes). If the list can't be loaded the supplier stays blank rather than failing the extraction.
4. **CRM entry** (`routes/crm.py`, `services/crm_api.py`, `frontend/src/components/DcSubmitPanel.tsx`): DCs go straight to the CRM's DC Inward API, there is no browser automation any more. The provider's guide is `DC-Inward-Purchase-Entry-API-Guide.docx`, kept outside the repo. **A save raises stock immediately and can't be edited or cancelled through the API**, so the flow is deliberately two steps: `POST /crm/dc/check` runs the CRM's checks and saves nothing, then `POST /crm/dc/save` saves. The check answers with hard errors (fix the value, or leave the row out and add it on the CRM screen) and questions (a person must tick each one, the guide forbids confirming them automatically). The panel greys out Save whenever the table or DC details differ from what was last checked, and its Notes box says only what's left to do: which rows to leave out (with one button for all of them), which to tick, or to check again. Every table row has a Leave out tick box. Leaving out a row with no error, and saving with any rows missing, each ask first: a DC with rows left out is emergency-only, for when a product has to be billed now. Save also stays off when the DC Date is more than 7 days old (`MAX_DC_AGE_DAYS`), because extraction sometimes misreads the year and the CRM accepts old dates without asking. `crm_api.py` resolves names to IDs: suppliers and staff from the CRM's `context`, products through `products/search`, matched on the exact name and never the first result, because the right product isn't always first. Some CRM products share a name and differ only by pack, so the row's `matched_pack` decides, and a tie (same name and pack on two CRM records) is never guessed: `PRODUCT_AMBIGUOUS` turns the row red. The search returns at most 20 results with no paging, so a very short name like `RIO` that's buried in longer ones can't be found and shows as not in the CRM. The expiry is normalised with `_fmt_expiry`, since the CRM refuses `08-27`. Rate 0 gets a question of our own (`RATE_ZERO`) because the CRM accepts it silently and an unread rate comes out of extraction as exactly that.
   - **Created By vs Checked By:** Checked By (`checkedByEmployeeId`) accepts any CRM employee. Created By comes from the `X-Employee-Id` header, which the CRM only allows for employees set up for that branch. We send the Checked By person there and fall back to `CRM_DEFAULT_EMPLOYEE_ID` on a 403. This is a setting on the CRM's employee record, nobody signs in to the CRM.
   - **Never show or log raw CRM error text.** The test server has returned an unhandled database error whose text included the server's database login, with code `VALIDATION_ERROR`, so the code alone proves nothing. Only report messages and text in the known validation shapes get through, filtered by `_safe_text`/`_validation_issues`; everything else becomes `GENERIC_ERROR`. The logs only get a status and a tidy code (`_log_code`). `_LEAK_RE` mustn't block the bare word "password": the CRM's own `MRP_NEEDS_ADMIN` message uses it. That error came from two simultaneous saves of one DC, which is why saves run one at a time under `_save_lock`.
   - **Duplicate protection:** `/crm/dc/check` returns a fresh `save_key`, sent as the `Idempotency-Key`. Any `/crm/dc/save` failure other than 400/409 means the outcome is unknown, including a CRM 5xx, since a gateway can fail after the CRM has committed. The panel then locks everything except Save, which retries that exact request with the same key (`pendingSave`), so the CRM treats it as the same save. Check is locked too, because a new key at that moment could create a second DC.
   - **Stage 3:** after a save, `_report_stage3` posts to `dc_pipeline` (`POST {DC_PIPELINE_URL}/stage3/save`) with the CRM's `refNo` as `reference_no`, so it's credited on that app's leaderboard. `dc_pipeline` matches `checked_by` by exact name against its own employee list, so a CRM name missing from that list gets no credit.
   - **Supplier mistakes from red pen marks** (`services/pen_marks.py`): staff use a red pen only when the supplier's DC is wrong. Once extraction has finished, `/extract` starts a background scan: a free colour check on each invoice page (`has_red_ink`, which evens out the light first and leans towards false alarms, since one costs a cheap AI read while a miss loses the mistake; its settings came from simulated pens and AI-edited photos, not yet a real red-pen DC), and an AI read only for pages with red (`MARKS_MODEL`, Pro, because Lite invented marks in testing). Pro can still invent one on a page with red print, so it must give each mark's location and `_red_at` drops any mark with no red ink at that spot. The `scan_id` comes back in the extract response, and `/crm/dc/save` hands it to `report_later`, which waits for the scan and posts the marks and photo to `dc_pipeline` (`POST {DC_PIPELINE_URL}/stage3/mistakes`) for its Supplier Mistakes dashboard. This must never affect extraction or saving, so failures are only logged, and a DC that's never saved records nothing. Scans live in memory, capped at `_MAX_SCANS` and 24 hours, so a backend restart loses any not yet reported. Changing the invoice pages after Extract clears the `scan_id`, so a supplier can't be blamed from the wrong photo.
5. **Voice corrections** (`routes/voice.py`): audio is transcribed by ElevenLabs Scribe v2, then a Gemini call (JSON mode, `MATCHING_MODEL`) parses the transcript into either per-row `updates` (field/value on a product row) or `dc_updates` (header fields); `checked_by`/`supplier` values are then fuzzy-matched against the CRM's lists, ignoring punctuation because the CRM spells some staff like `Renuka.D.H`.
6. **Inbox** (`routes/inbox.py` + `App.tsx`'s `InboxUploadPage`): a separate lightweight route, reached at `/inbox-upload` (checked via `window.location.pathname` in `App.tsx` rather than a router), meant to be opened on a phone (via the stable domain the app is served on) so someone can snap invoice photos on-site. Uploaded images land in `backend/inbox/`; the main desktop page polls `GET /inbox` every 10s and shows thumbnails. Clicking a thumbnail routes it by `photo_type` (see below) into the right upload slot and removes it from the inbox — it no longer triggers extraction automatically; the user reviews the model/reasoning settings and clicks "Extract Products" themselves. Files that are never clicked (abandoned uploads) are swept up by a background task (`inbox_cleanup_loop` in `routes/inbox.py`, started via `main.py`'s `lifespan`) that deletes any inbox file older than 24h, checked once every 24h — plus an immediate pass on backend startup so files already stale when the server restarts don't wait a full day.
   - **Pipeline import** — a second, non-phone way for images to land in the same inbox. `GET /inbox/pipeline-suppliers` and `POST /inbox/import-from-pipeline?dc_number=&supplier_id=` call out to `dc_pipeline` — a separate, unrelated app (own FastAPI + SQLite, own repo, no git relationship to this one) that runs a two-stage DC-photo-logging workflow *before* this app's extraction step, normally on `http://localhost:3002` (configurable via `DC_PIPELINE_URL`). Import fetches the `invoice`/`corrected`/`package` photo types for a given `(dc_number, supplier_id)` via `dc_pipeline`'s existing `/stage2/find` + `/photos/{id}` endpoints, and writes the raw response bytes straight to disk with no re-encoding — verified byte-for-byte identical (SHA256) to the original camera file, so resolution/EXIF survive intact. This is a one-way, read-only, server-to-server call: `dc-entry-automation` never opens `dc_pipeline`'s database or files directly, and `dc_pipeline` needed zero changes to support it — deliberate, to avoid coupling to its internal schema. If `dc_pipeline` is unreachable → clean `502`; if the DC doesn't exist there → clean `404`; if a specific photo already aged out of `dc_pipeline`'s own 15-day photo-retention cleanup (`_photo_cleanup_loop` in its `main.py`, unrelated to this app) → that one photo is skipped rather than failing the whole import. The Inbox section of `App.tsx` has a matching supplier dropdown (populated from `dc_pipeline`'s real `supplier_id`s — a different set of IDs than the CRM's) + DC-number input + "Fetch from Pipeline" button.
   - **Photo type routing**: each inbox item carries a `photo_type` (`invoice`/`corrected`/`package`), inferred from a filename prefix (`_infer_photo_type` in `routes/inbox.py`) that pipeline-imported files get stamped with at write time; phone/manual uploads have no prefix and default to `invoice`. `App.tsx` uses this to route a clicked thumbnail: `package` → the "Product's Image" box; anything else → appended to `invoiceFiles` (see below) if it's under the 2-page cap. If already at the cap, the click is a no-op and the photo stays in the inbox rather than being lost — a DC with more than 2 non-package photos (e.g. several `corrected` re-uploads) will need one removed first before the rest can be used.

### Admin page (`routes/admin.py`, `frontend/src/components/AdminPage.tsx`)

Reached at `/admin` — same lightweight `window.location.pathname` branch pattern as `/inbox-upload` (with a trailing-slash normalization so both `/admin` and `/admin/` resolve there), linked from a nav link in the home page header. PIN-gated (`ADMIN_PIN` in `config.py`, default `2009`), enforced **server-side** via one `Depends(_require_admin_pin)` at the `routes/admin.py` router level — covers every route on it including `/admin/verify-pin` itself (the frontend's "unlock" call), so there's a single auth mechanism, not a client-side check plus a separately-implemented real one. It manages one thing (suppliers and staff are managed in the CRM):

- **Product catalog upload** — `POST /admin/product-list` validates an uploaded `.xlsx` by constructing a throwaway `ProductMatcher` from it *before* touching the live file (`KeyError`/`ValueError`/`InvalidFileException` all become clean 400s — note `ProductMatcher.__init__` leaves its `openpyxl` read-only workbook handle open when it raises partway through, so the temp file's cleanup in `admin.py`'s `finally` is itself wrapped in try/except; a first version of this let that Windows file-lock `PermissionError` mask the clean 400 as an unhandled 500, caught by live-testing the rejection paths, not by inspection). Once validated, `admin.py` backs up the current `Product_List.xlsx` to `Product_List.backup.xlsx` (single rolling backup, overwritten each upload) with a plain `shutil.copy2`, then calls `services/matcher_instance.py`'s `replace_catalog_file()` to actually swap it in — **not** a bare file copy from `admin.py` itself. That function does the copy-to-temp + `os.replace()` swap *and* the matcher rebuild together, under the same `threading.Lock()` that guards `get_matcher()`'s build path, so the two can never interleave. This isn't optional hardening — a first version had `admin.py` doing its own unsynchronized `os.replace()` and calling `reset_matcher()`/`get_matcher()` as separate steps, and it broke under a live concurrency test (8 threads hammering `/products/search` — a sync `def`, so FastAPI thread-pools it — while an upload ran): `os.replace()` failed with Windows `WinError 5: Access is denied`, because a concurrent matcher build had the destination file open for reading without `FILE_SHARE_DELETE`, which `os.replace` requires on Windows. The same test also revealed `get_matcher()` had no lock on its *build* path either — concurrent cache-misses would each independently rebuild the whole ~11,500-family index. One shared lock in `matcher_instance.py`, covering both `get_matcher()`'s build and `replace_catalog_file()`'s swap, fixes both: re-ran the same 8-threads-hammering-search-during-an-upload test afterward with zero errors. If `replace_catalog_file()` fails (for either the primary upload or, on failure, the backup), the caller in `admin.py` reports a 500 with detail on what happened; a rollback that itself fails is called out explicitly as needing manual attention rather than silently swallowed. All exercised live, not just written: bad files rejected with the live catalog byte-for-byte unchanged, a good upload found via `/products/search` with no restart, the rollback branch itself, and the full concurrency scenario above.

**Not solved here, and required before pointing this at the live CRM:** this backend is reachable from the public internet (`dc.shubhada.live`) and has no login on any route except a 4-digit PIN with no rate-limiting on `/admin`. Now that `/crm/dc/save` writes straight to the CRM, a stranger's request could raise real stock.

`vite.config.ts`'s dev proxy for `/admin` is a trailing-slash regex (`^/admin/`), not a plain prefix — bare `/admin` is the frontend's own page route, and a plain-prefix proxy would instead send that page-load request to the backend (where nothing matches it), breaking `/admin` under `npm run dev` only; prod is unaffected since `main.py` serves everything on one port there. Verified both ways live: `curl localhost:5173/admin` returns Vite's `index.html`, `curl localhost:5173/admin/verify-pin` reaches the backend.

### Config and shared data (`config.py`)

Loads `.env`: OpenRouter/ElevenLabs keys, `PORT`, `ALLOWED_ORIGINS`, `PRODUCT_LIST_PATH`/`PRODUCT_LIST_SHEET`, `DC_PIPELINE_URL`, `ADMIN_PIN`, and the CRM API settings (`CRM_API_BASE_URL`, `CRM_CLIENT_ID`, `CRM_CLIENT_SECRET`, `CRM_DEFAULT_EMPLOYEE_ID`, plus `CRM_BRANCH_IDS`, which maps the frontend's branch names to the CRM's ids). `CRM_API_BASE_URL` has no default on purpose, since a save raises real stock. `app.shubhadahealth.com` is the test server; the live API address isn't known yet (the live CRM at `shubhadahealth.com:7007` has no API at that address). Supplier and staff names aren't stored here, they come from the CRM.

**Security note:** the CRM web login used to be hardcoded in `routes/browser.py` (since removed) and was exposed in this repo's git history while it was public on GitHub — that history was not rewritten. If the CRM password shown in old commits was never rotated at the source, treat it as still compromised.

### Frontend state (`frontend/src/App.tsx`)

Single top-level component holding all state; no router, no state library. The Supplier and "Checked By" lists come from `GET /suppliers` and `GET /staff` on mount, which both serve the CRM's names; if they fail, the DC Details card says so rather than showing empty dropdowns. Shared style-object constants (`labelStyle`/`labelText`/`inputStyle`) live in `frontend/src/styles.ts` so `AdminPage.tsx` can reuse them without duplicating them or creating a circular import (`App.tsx` imports `AdminPage`, so the reverse can't also be true). Key DC fields and the extracted product table are persisted to `sessionStorage` (`dc_products`, `dc_number`, `dc_date`, `dc_supplier`, `dc_checked_by`, `dc_branch`, `dc_scan_id`) so a page refresh mid-entry doesn't lose them. Corrections typed into the table, Change picks and Leave out ticks are React state and are lost on a refresh.

Invoice pages are `invoiceFiles: File[]` (0–2 items, object-URL previews in `invoicePreviews` kept in sync via a `useEffect` that revokes stale URLs), fed through a single `handleInvoiceFilesChange` that only resets the rest of the form (`resetEntryState`) when going from 0 files to 1+ — adding a second page to an in-progress entry doesn't wipe `dc_number`/`products`/etc. `components/ImageUpload.tsx` is the shared upload widget for both this and the separate "Product's Image" box: it takes `selectedFiles`/`previewUrls` arrays and a `maxFiles` prop (default 1). At `maxFiles === 1` (Product's Image) it behaves as a classic single-file picker (click-to-replace, one big "Remove" button); at `maxFiles > 1` (invoice, `maxFiles={2}`) the same drop zone/browse/camera **adds** photos instead of replacing until the cap is hit, each with its own small "×", and the drop zone hides itself once full — the only way to swap a photo at the cap is to remove one first.
